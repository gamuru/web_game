# Game QA Verification — 정합성 검증 절차

이 스킬은 `qa-tester` 에이전트가 사용한다. 에이전트 정의(`qa-tester.md`)에 검증 대상과 우선순위가 정리되어 있으므로, 여기서는 **실제로 무엇을 실행해서 대조하는지** 구체적 절차를 다룬다.

## 핵심 원칙: 존재 확인이 아니라 교차 대조

"씬 파일이 있다"는 정상 동작의 증거가 아니다. "등록된 씬 목록과 실제 호출되는 씬 키가 정확히 일치한다"가 증거다. 아래 모든 절차는 반드시 **선언부와 사용부를 함께 추출**한 뒤 diff처럼 비교한다.

## 1. 씬 그래프 대조

```bash
# 등록된 씬 (game config)
grep -n "scene:" src/config/gameConfig.ts -A 20

# 실제 씬 전환 호출
grep -rn "scene.start(\|scene.launch(\|scene.switch(" src/
```
등록된 씬 클래스명 목록과, 호출부 문자열 인자(또는 클래스 참조)를 비교한다. 다음을 확인한다:
- 등록되었지만 어디서도 호출되지 않는 씬 (죽은 씬 — 의도적인 최초 씬 제외)
- 호출되지만 등록되지 않은 씬 키 (오탈자 → 런타임에 조용히 실패하거나 에러)

## 2. 에셋 키 대조

```bash
# 로드 선언
grep -rn "this.load.image(\|this.load.audio(\|this.load.atlas(\|this.load.spritesheet(" src/

# 사용처 (add.sprite, add.image, sound.add, play 등)
grep -rn "add.sprite(\|add.image(\|sound.add(\|texture(" src/
```
`ASSET_KEYS` 상수(`phaser-mobile-dev` 스킬 권장 패턴)를 쓰고 있다면 상수 정의와 실제 사용을 대조하는 편이 오탈자 검출에 더 신뢰도가 높다. 문자열 리터럴을 직접 쓰는 코드가 있으면 특히 주의 깊게 대조한다 — 같은 값처럼 보이는 오탈자(`enemy-basic` vs `enemy_basic`)를 놓치기 쉽다.

## 3. 입력 바인딩 ↔ 히트 영역 대조

```bash
grep -rn "setInteractive(\|pointerdown\|pointerup\|on('tap'" src/
```
각 인터랙티브 요소에 대해:
- 실제 화면상 크기(스프라이트 원본 크기 × 스케일)가 최소 44x44px(CSS px 환산) 이상인지 확인
- 여러 인터랙티브 요소가 겹쳐 있어 의도치 않은 요소가 터치를 가로채지 않는지(z-order, depth) 확인

## 4. 저장 데이터 스키마 대조

```bash
grep -rn "localStorage.setItem\|SaveManager" src/systems/
```
`SaveManager` 클래스가 있다면(권장 패턴), 저장 시 쓰는 객체의 필드와 로드 시 읽는 코드의 필드 접근을 나란히 놓고 비교한다. 특히:
- 옵셔널 필드를 로드 시 기본값 없이 바로 사용하는 곳 (undefined 접근 크래시 위험)
- 버전 필드(`version`)가 있다면, 버전별 마이그레이션 분기가 실제로 존재하는지

## 5. 상태 전이 대조

게임 상태(메뉴/플레이/일시정지/게임오버 등)가 명시적 상태 머신이나 enum으로 정의되어 있다면:
```bash
grep -rn "GameState\.\|gameState =" src/
```
정의된 전이 목록과, 코드에서 실제 상태를 변경하는 모든 지점을 나열해 대조한다. 중간 상태에서 최종 상태로 가는 경로가 막혀 있지 않은지 특히 확인한다(예: "일시정지"에서 "게임오버"로 갈 방법이 코드상 없는 경우).

## 6. 실행 기반 검증

정적 대조로 끝내지 않는다. 가능하면 아래를 실행한다:

```bash
npm run build   # 타입/빌드 에러 확인
npm run dev     # 개발 서버 기동
```
개발 서버가 뜨면 브라우저에서 실행하고:
- DevTools 콘솔에 에러/경고가 없는지 확인 (특히 404 — 에셋 경로/키 오류의 직접적 증거)
- DevTools의 기기 툴바(모바일 뷰포트 에뮬레이션)로 최소 2개 이상의 화면 크기에서 레이아웃 확인
- 실제로 탭/드래그해보고 반응하는지 확인 (마우스 클릭은 터치와 판정이 다를 수 있음에 주의)

## 7. 크로스 디바이스 테스트 매트릭스

실기기 접근이 제한적이면 최소한 아래 화면 비율을 DevTools 에뮬레이션으로 확인한다:

| 프로필 | 대표 비율 | 확인 포인트 |
|--------|----------|-------------|
| 좁고 긴 화면 | 9:19.5 (예: 최신 아이폰/안드로이드) | 세이프에어리어, 하단 UI가 홈 인디케이터에 가리지 않는지 |
| 작은 화면 | 9:16 구형 소형 기기 | 텍스트/버튼이 잘리지 않는지, 최소 히트 영역 유지 |
| 태블릿 | 3:4 ~ 4:3 | 레터박스(FIT 모드)가 과도하게 크지 않은지 |
| 가로 모드 | 지원 대상이면 확인 | 방향 전환 시 UI 재배치, 미지원이면 회전 안내 표시 |

## QA 리포트 작성 규칙

`qa-tester.md`에 정의된 출력 형식을 따르되, 각 결함 항목에는 반드시:
1. 파일:라인 (또는 grep 결과 근거)
2. 재현 조건 ("어떤 화면 크기/입력에서")
3. 기대 동작 vs 실제 동작

이 세 가지가 없는 "~인 것 같다" 수준의 보고는 담당 에이전트가 재현할 수 없어 수정이 지연된다.
