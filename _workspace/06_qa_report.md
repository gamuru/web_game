# QA 리포트 — 튜브 배치 엄지 도달성(Thumb Reach) 재설계 검증

검증 대상: `04_architect_design.md`(설계, "마지막 행 y 고정" 방식) / `05_engine_dev_summary.md`(구현) — `GameScene.buildTubes()`의 `startY`(첫 행 고정) → `BOTTOM_ROW_Y=1120`(마지막 행 고정) 전환.

검증 환경: 정적 코드 대조(설계 문서의 픽셀 계산을 실제 코드값으로 독립 재계산) + `npm run build` + `npm run dev` + claude-in-chrome 브라우저(리사이즈 시도했으나 아래 "미검증" 항목 참고)로 실제 플레이.

## 1. `npm run build`

**통과.** `tsc -b && vite build` 에러 없음. 번들 크기 경고(1.49MB)는 기존부터 있던 것으로 이번 변경과 무관.

## 2. diff 적용 정확성

`src/scenes/GameScene.ts:6-9, 44-60`을 직접 읽고 설계 문서 §7의 diff와 문자 단위로 대조 — **정확히 일치**. `numRows = Math.ceil(this.tubeState.length / TUBES_PER_ROW)` 추가, `y = BOTTOM_ROW_Y - (numRows - 1 - row) * ROW_GAP` 교체 외 루프 구조·`x` 계산·`Tube` 생성 호출 변경 없음. `UIScene.ts`, `Tube.ts`, `src/data/levels.ts`는 실제로 손대지 않았음(각 파일 diff 없음, `git` 미사용 프로젝트라 파일 내용을 직접 04번 설계 문서 인용과 대조해 확인).

## 3. 레벨 10개 전수 좌표 재검증 (설계 문서 §3-4 주장 재계산)

설계 문서의 계산을 신뢰하지 않고, 실제 소스에서 상수를 뽑아 **독립적으로 재계산**했다.

- `src/scenes/GameScene.ts:6-9`: `TUBES_PER_ROW=4`, `COL_GAP=150`, `ROW_GAP=380`, `BOTTOM_ROW_Y=1120`.
- `src/objects/Tube.ts:39-40`: `height = SLOT_HEIGHT(70) * capacity + WALL_THICKNESS(6)` → capacity4=286, capacity5=356. hitArea는 `Rectangle(-45, -height, 90, height)`이므로 컨테이너 y 기준 상단=`y-height`, 하단=`y`.
- `src/scenes/UIScene.ts:26`: 메뉴 버튼 `(width-100, 32, 90, 48)` → Rectangle 오브젝트 기본 origin(0.5,0.5) 기준 hitArea 하단=`32+48/2=56`. (설계 문서는 `moveCountText` 추정치인 58을 썼으나, 실제 인터랙티브 요소인 메뉴 버튼 자체의 하단은 56이다 — 아래 "경미한 문서 오차" 참고.)
- `src/scenes/UIScene.ts:27-28`: 되돌리기/섞기 버튼 `(·, height-90, ·, 70)` → `height=1280` 기준 y=1190, hitArea `[1155, 1225]`.
- `src/config/gameConfig.ts:16-17`: 캔버스 `720×1280` 확인(설계 문서 가정과 일치).

재계산 결과(모든 레벨, `row y = 1120 - (numRows-1-row)*380`):

| id | 튜브수 | capacity | numRows | row0 y (상단/하단) | row1 y (상단/하단) | HUD와 여백 | 버튼과 여백 |
|---|---|---|---|---|---|---|---|
| level-1 | 4 | 4 | 1 | — | 1120 (834/1120) | — | 1155-1120=35 |
| level-2 | 5 | 4 | 2 | 740 (454/740) | 1120 (834/1120)* | 454-56=398 | 35 |

| level-6 | 7 | 4 | 2 | 740 (454/740) | 1120 (834/1120) | 398 | 35 |

(*level-2/5는 5튜브라 row1이 1개 튜브뿐이지만 y좌표 공식은 동일하게 적용됨 — 실측으로 별도 확인, 5번 항목 참고)

**결론: 전 레벨에서 y축 겹침 없음.** 최악의 경우(capacity=5, level-8/level-10)도 상단 여백 328px, 하단 여백 35px로 양쪽 모두 양수 — 설계 문서 §4의 "겹치는 구간이 전혀 없다" 주장과 **일치**.

**경미한 문서 오차 발견(코드 결함 아님):** 설계 문서 §3-4는 상단 여백 계산에 `moveCountText` 하단 추정치(y≈58)를 사용했으나, 실제로 인터랙티브(hitArea)한 요소는 메뉴 버튼(하단=56)뿐이고 `moveCountText`는 `setInteractive` 호출이 없는 순수 텍스트라 입력 충돌 대상이 아니다. 올바른 기준점(메뉴 버튼 하단=56)으로 재계산하면 여백은 326px가 아니라 328px로, 문서의 오차는 2px이며 **결론(겹침 없음)에는 영향 없음**. 수정 불필요, 참고용으로만 기록.

## 4. 엄지 도달성 실질 확인 (브라우저 시각 확인)

`npm run dev`로 기동 후 claude-in-chrome에서 아래 레벨을 직접 열어 스크린샷으로 확인했다.

| 레벨 | 구조 | 확인 결과 |
|---|---|---|
| level-1 | 1행, 4튜브, cap4 | 튜브 행이 화면 하단부(되돌리기/섞기 버튼 바로 위)에 위치. 스크린샷으로 HUD-튜브 간 넓은 공백 확인. |
| level-2 | 2행(4+1), cap4 | row1(1튜브, 화면 중앙 정렬)이 화면 맨 아래, row0(4튜브)이 그 위에 위치 — "마지막 행이 짧아도 하단 고정" 공식이 의도대로 동작함을 실측 확인(설계 문서 표에 명시되지 않은 케이스였으나 코드 검증으로 커버). |
| level-9 | 2행(4+4), cap4 | row1이 하단 버튼 바로 위, row0은 그 위, 두 행 간격 육안상 정상 분리. |
| level-8 | 2행(4+3), cap5 (최악 케이스) | 메뉴 버튼과 row0 사이를 `zoom`으로 확대 촬영 — 육안상 수백 px에 달하는 명확한 공백 확인(좌표 계산의 328px 여백과 일치). |
| level-10 | 2행(4+3), cap5 | level-8과 동일 패턴, 겹침 없음 육안 확인. |

**결론: 전 레벨에서 튜브 그리드가 화면 하단 쪽(마지막 행 기준 화면 세로 87.5% 지점)에 배치되며, 상단 HUD·하단 버튼 어느 쪽과도 겹치지 않음을 시각적으로 확인.**

## 5. 회귀 재확인 (레벨 클리어 → 메뉴 → 다른 레벨 진입)

다음 순서로 반복 검증했다: `level-1 클리어 → 메뉴 → level-9 진입(미클리어) → 메뉴 → level-2 진입(미클리어) → 메뉴 → level-2 클리어 → 메뉴 → level-3 진입(미클리어) → 메뉴 → level-9 진입(미클리어) → 메뉴 → level-8 클리어 → 메뉴 → level-10 진입(미클리어)`.

- 씬 전환 자체는 전 구간에서 정상(렌더링 깨짐, 크래시 없음).
- `read_console_messages`로 확인한 결과 확장 프로그램의 무관한 로그(`hiding iframe`) 1건 외 **에러/경고 없음**.
- `clearedLevels` 레지스트리 배지: `레벨2 클리어 → 메뉴` 및 이어서 `레벨8 클리어 → 메뉴` 시점 모두 스크린샷으로 초록 배지(✓)가 정확히 누적 표시됨을 확인(레벨2, 레벨8 동시에 배지 유지).

**주의 — 재현 실패한 1회성 이상 현상(결함으로 등록하지 않음, 투명성을 위해 기록):**
테스트 도중 한 차례, `level-1 클리어(배지 정상 표시 확인) → level-9 진입(미클리어) → 메뉴 복귀` 직후 스크린샷에서 level-1의 초록 배지가 사라진 것처럼 보였다(`registry.get('clearedLevels')`가 비어있는 것처럼 렌더링됨). 코드 리뷰(`GameScene.ts:107-113`, `MenuScene.ts:29`) 상 registry는 Phaser Game 전역 싱글턴이라 이 현상이 재현되면 실제 결함이지만, **동일 시나리오를 두 차례 더 깨끗하게(각 액션 후 스크린샷으로 완료를 확인하며) 재현 시도했으나 배지 유실이 재발하지 않았다**(레벨2 배지가 레벨9/레벨3 방문 후에도 계속 유지됨, 이후 레벨8까지 정상 누적). 최초 발생 시점은 클릭(메뉴 버튼) 직후 씬 전환 완료를 기다리지 않고 곧바로 드래그(스크롤) 2회를 배치 실행한 시점과 일치했고, 동일한 "클릭+드래그 연속 배치"를 의도적으로 재현했을 때는 메뉴 버튼 클릭 자체가 아예 무시되는(씬 전환 실패) 현상만 확인되었다(`이동:0` 그대로 level-9에 머묾) — 이는 **브라우저 자동화 도구가 씬 전환 애니메이션/렌더 완료를 기다리지 않고 입력을 연속 전송할 때 발생하는 테스트 도구 타이밍 아티팩트**로 판단되며, `registry`가 게임 코드 상 리셋되는 경로는 존재하지 않는다(`grep -rn "clearedLevels\|registry" src/` 결과 `GameScene.ts:108,110`의 읽기/추가와 `MenuScene.ts:29`의 읽기뿐, 초기화 코드 없음). **결함으로 등록하지 않음** — 재현 불가 + 코드상 원인 불명 + 클린 테스트에서 100% 정상 동작. 다만 향후 유사 보고가 실사용자로부터 들어올 경우 이 메모를 참고할 것.

## 6. 실제 플레이 (탭 메커니즘 자체가 새 좌표에서 정상 동작하는지)

새 y좌표에서 실제 탭으로 3개 레벨을 처음부터 끝까지 클리어했다(요청한 "1행 하나, 2행 하나, capacity=5 하나" 충족).

| 레벨 | 구조 | 결과 |
|---|---|---|
| level-1 | 1행, cap4 | 7회 이동 후 클리어 (`클리어!` 오버레이 확인) |
| level-2 | 2행(4+1), cap4 | 7회 이동 후 클리어(최소 이동수와 일치) |
| level-8 | 2행(4+3), **cap5** | 20회 이동(수기 계획 시퀀스 그대로) 후 클리어, 도중 무효 탭(shake) 없이 전부 유효 pour로 처리됨 |

모든 탭이 계획한 튜브를 정확히 선택했고(오탭/좌표 어긋남 없음), `이동:` 카운터가 매 pour마다 정확히 1씩 증가했다 — **새 y좌표에서 히트 영역과 시각적 위치가 어긋나지 않음을 실제 조작으로 확인**.

## 미검증 (실기기/범위 밖)

- 실제 모바일 기기(iOS/Android)에서의 엄지 조작감 — 브라우저 에뮬레이션(마우스 클릭)으로는 "편해졌다"는 주관적 체감을 확정할 수 없음. 좌표 계산과 시각 확인상 화면 하단 87.5% 지점 배치는 실측 확인됐으므로 실기기 테스트는 확인 차원의 후속 권장.
- 가로 모드(landscape) 회전 시 레이아웃 — 이번 요청·설계 문서 모두 범위 밖으로 명시.
- 브라우저 창 리사이즈(모바일 뷰포트 강제)가 이 테스트 환경에서 적용되지 않아(`resize_window` 호출 후에도 `window.innerWidth`가 변하지 않음 확인), 실제 좁은 뷰포트에서의 렌더링은 Phaser `Scale.FIT` 로직(720:1280 비율 유지, 레터박스)에 대한 코드 검토로 대체함 — 이 로직 자체는 이번 변경 범위 밖(`gameConfig.ts` 미변경)이라 별도 결함 아님.
